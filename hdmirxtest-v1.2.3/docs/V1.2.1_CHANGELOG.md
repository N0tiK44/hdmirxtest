# V1.2.1 — safe bridge negotiation and recovery

## Root cause addressed

Older `restoreedid` behavior trusted `/var/tmp/hdmirx-edid-backups/
rx-edid-original.bin` without constraining its modes or capabilities. That file
could be the stock 4K-capable `RK-UHD` profile or another stale EDID. Exposing
it while Windows was attached could force immediate display re-enumeration and
destabilize the host's dual-display topology.

## New safety contract

- EDID writes are refused while an active HDMI-RX source is detected.
- Setup reads only the single connected HDMI-TX sink.
- The advertised mode set is the sink/RK3588 intersection with hard ceilings:
  1920x1080, 240 Hz and 600 MHz pixel clock.
- The bridge advertises fixed-rate RGB 8-bit SDR and removes DSC, FRL, HDR,
  VRR/FreeSync, YCbCr, deep colour and unknown timing-bearing capabilities.
- The bridge uses the unique `RKP / RK-BRIDGE` identity and a stable serial
  derived from the sink EDID, preventing reuse of the monitor's direct-connect
  Windows cache.
- Candidate installation is transactional: generate, audit, write, read back,
  byte-compare and audit again. Failure loads an independently generated safe
  recovery EDID.
- `restoreedid` now loads only an audited 1080p60 RGB 8-bit recovery profile.
  It never selects the old stock/original backup.
- Live passthrough refuses to start unless the active HDMI-RX EDID passes the
  bridge audit.
- Alpine/OpenRC receives an early-boot service that reapplies the verified
  bridge EDID from `/var/lib/hdmirxtest/bridge-edid.bin`.

## Scope boundary

This is a decoded HDMI capture-and-rescan bridge, not a transparent electrical
repeater. DSC, FRL, HDCP and VRR are not forwarded. A monitor mode appears only
when the downstream sink advertises it and it falls inside every bridge cap.
The BGR3/RGB888 and NV24/NV24 DMA-BUF paths remain copy-free.
